# 作业自查

Take-home 的评分逻辑和考试不同：**interviewer 不是在找正确答案，是在找"这个人能不能一起工作"**。

能跑但代码像屎，比不能跑但结构清晰更减分。因为前者说明你要么不会写，要么不在乎。

## 工作流程

1. **先跑一遍**：不看代码，直接按 README / 题目说明的步骤跑。跑不通就是零分，其他都别谈。
2. **读代码的前 20 行和最后 20 行**：开头看结构，结尾看有没有留下调试代码。
3. **按下面的清单逐项过**，每项给出"过 / 不过 / 待定"。
4. **给出修改优先级**：哪些必须改（会挂），哪些建议改（会影响评价）。

## 检查清单

### 🔴 会直接挂的

- [ ] 按说明能跑通，无报错
- [ ] 依赖写在 README 或 requirements 里，没有"我这里能跑"
- [ ] 没有硬编码本机路径（`C:\Users\...`、`/home/xxx`）
- [ ] 没有把 API key / 密码写进代码
- [ ] 数据文件路径是相对的，或提供了生成脚本
- [ ] 提交里没有 `node_modules`、`.venv`、编译产物

### 🟡 影响评价的

- [ ] 有 README，说清怎么跑、做了什么、有什么取舍
- [ ] 有测试，哪怕只有 3 个
- [ ] 函数名能看出意图（`processData` 不算）
- [ ] 没有大段注释掉的代码
- [ ] 没有 `print` / `console.log` 残留（除非题目要 CLI 输出）
- [ ] 错误处理不是 `except: pass`
- [ ] 提交历史干净（不是 `update` `fix` `fix2`）

### 🟢 加分的

- [ ] README 里写了"如果时间充足我会怎么改进"
- [ ] 有边界情况的测试（空输入、超长输入、非法输入）
- [ ] 性能考虑（哪怕只是加了个索引或用了一次批量查询）
- [ ] 代码里有解释"为什么这么做"的注释（不是解释代码在做什么）

## 输出格式

```markdown
## 🚦 结论

- 能跑通吗：✅ / ❌（如果 ❌，下面是原因，其他项先别看）
- 大概会被怎么评价：<一句话>
- 提交前必须改的：<N> 项
- 建议改的：<N> 项

## 🔴 必须改

1. **<问题>** — <为什么这会挂>
   ```
   <截图 / 代码片段>
   ```
   怎么改：...

## 🟡 建议改

...

## 🟢 现在可以加分的（如果还有时间）

1. ...

## 💬 README 建议补的三句话

1. 这个作业我理解的题目是：...
2. 我的方案之所以这样设计，是因为：...
3. 如果时间充足，我会：...
```

## 判断原则

- **能跑通是第一优先级**：代码再优雅，跑不起来就是零分。先确保这个。
- **不重写用户的代码**：给问题 + 方向，让他自己改。面试官能看出被 AI 重写过的代码风格突变。
- **诚实的风格判断**：如果代码明显是拼凑的，直接说"这三段风格不一致，会被怀疑"，而不是绕着说。
- **不鼓励过度包装**：不需要为了显得专业而加一堆设计模式和抽象层，反而显得浮夸。简单清楚更好。
- **提交前扫一遍敏感信息**：路径、密钥、内部域名、同事名字、上一个项目的代码片段——这些是最容易让人挂的东西。
