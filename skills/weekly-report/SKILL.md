# 周报

周报不是流水账，是**一次低成本的向上管理**。leader 一周只见你几面，周报是你唯一能控制的信息渠道。

大多数人写成了"做了什么"，而 leader 想看的是"进展如何、有什么卡点、下一步要什么"。

## 工作流程

1. **先问三个问题**（用户没说时）：
   - 这周实际完成了什么？（哪怕是"读完了某模块代码"也算）
   - 有什么卡住了？卡在谁那里？
   - 下周最重要的三件事是什么？
2. **把"做了"翻译成"推进了什么"**：
   - 差：`学习了 Redis`
   - 好：`梳理了订单服务的缓存用法，发现 3 处未设过期时间的 key，已提交修复 PR`
3. **标出可见度低但重要的工作**：写文档、排查线上问题、帮别人 review——这些容易被自己忽略，但恰恰是 leader 想知道的。
4. **风险必须写**：不写风险，出问题时就是"你没提前说"。

## 输出格式

```markdown
## 本周进展

**1. <一句话说清推进了哪件事>**
- 具体动作 + 结果（有数字给数字，没数字给范围）
- 影响：对谁有用 / 解决了什么

**2. ...**

## 卡点与风险

| 卡点 | 影响 | 需要谁 / 什么支持 |
|---|---|---|
| ... | ... | ... |

（没有卡点就写"无"，不要留空——留空会被理解成没想）

## 下周计划

1. <最重要的一件>（预计 <时间> 完成）
2. ...
3. ...

## 需要 leader 决策 / 协助的

- ...
```

## 判断原则

- **不要写成 git log**：提交记录 leader 自己能看，周报的价值是"为什么"和"接下来"。
- **数字要真实**：写"优化了 3 个接口，P95 从 800ms 降到 210ms"比"大幅优化性能"有用一百倍；如果没测过，就说"待压测验证"。
- **风险写得具体**：`可能延期` 没用，`因为等 XX 团队的接口联调，如果周三前拿不到，这个需求会滑到下周` 才有用。
- **不自我贬低，也不邀功**：用事实说话，不用"仅仅""只是"这类词削弱自己的产出。
- **长度控制**：一屏能看完。超过一屏，leader 只会看标题。
